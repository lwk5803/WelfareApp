기존엔 "회원 등록/수정/삭제" 메뉴 하나 안에 탭(`st.tabs`) 3개(신규등록/수정삭제/엑셀등록)로 묶여 있었는데, 각각 최상위 메뉴 항목으로 뺐고, 수정과 삭제도 서로 다른 메뉴로 나눔.

**왜**: 1·2차 외부 테스트 피드백 — "회원 등록/수정/삭제도 다른 메뉴들처럼 따로 보였으면 좋겠다, 관리하기 편할 것 같다."

**참고 개념**:
- Streamlit의 `st.sidebar.radio`는 사용자가 고른 값을 파이썬 변수로 그대로 돌려주는 라디오 버튼입니다. `if/elif` 사슬로 "지금 메뉴 값이 뭐냐"에 따라 화면을 다르게 그리는 구조라, 메뉴를 늘리는 건 그냥 `elif` 블록 하나를 추가하는 것과 같습니다.

## 2026-08-13 — #7 주소 검색: 건물명/상호명 검색 안 되던 문제 수정

**무엇을**: `address_api.py`의 `search_road_address()`가 카카오 "주소 검색 API"로 결과가 없을 때, "키워드 검색 API"로 한 번 더 시도하도록 fallback을 추가함. 결과 항목에 `place_name`(건물명/상호명)을 추가해서, `app_frontend.py`의 주소 선택 드롭다운에 건물명이 있으면 같이 보여주도록 함(`main.py`는 두 파일을 그대로 연결만 하고 있어서 변경 없음).

**왜**: 피드백 #7 — "주소 검색 시 구주소/도로명이 정확하지 않으면 검색 실패, 건물명으로 검색해도 빈 내용."
원인은 카카오의 "주소 검색 API"(`/v2/local/search/address.json`)가 정확한 지번·도로명 형식만 인식하고, 건물명·상호명(예: "롯데월드타워", "OO경로당")은 애초에 이 API가 다루는 범위가 아니었기 때문. 카카오 "키워드 검색 API"(`/v2/local/search/keyword.json`)를 fallback으로 붙여서 해결.

**검증**: `curl`로 "롯데월드타워" 검색 → 이전엔 빈 배열, 수정 후엔 도로명주소+건물명이 정상 반환됨. 기존 정확한 도로명 검색("서울 강남구 테헤란로 123")도 우편번호 포함해서 그대로 잘 동작하는 것 확인(회귀 없음).

**참고 개념**:
- 외부 API를 쓸 때는 "이 API가 정확히 뭘 검색해주는 API인가"를 문서에서 확인하는 게 중요합니다. 카카오는 같은 "주소 찾기"처럼 보여도 목적이 다른 API를 여러 개 제공합니다 — 정확한 주소 문자열 매칭용(주소 검색), 장소/건물/상호명 매칭용(키워드 검색). 하나로 안 되면 다른 API로 다시 시도하는 방식을 "fallback(대체 시도)"이라고 부릅니다.
- 우편번호(zip_code)는 "주소 검색 API" 결과에만 들어있고 "키워드 검색 API"엔 없어서, 건물명으로 찾은 주소는 우편번호가 빈 채로 나옵니다. 필요하면 나중에 우편번호만 별도 조회하는 API를 추가로 붙일 수 있습니다.

## 2026-08-13 — #2 로그인/권한 관리 추가

**무엇을**:
1. `sql/003_add_profiles_and_auth.sql` 추가 — `profiles` 테이블(사용자 id + role) 신설, `auth.users`에 새 계정이 생기면 자동으로 `profiles`에도 기본 role(`staff`)로 등록되는 트리거 포함. **⚠️ 이것도 Supabase SQL Editor에서 직접 실행 필요.**
2. `auth.py` 신규 — Supabase Auth로 로그인(`login()`)하고, FastAPI가 요청마다 로그인 토큰(JWT)이 진짜인지 검증하는 `require_user`/`require_admin` 두 개의 "문지기" 함수를 만듦.
3. `main.py` — `/api/auth/login` 엔드포인트 추가. 회원 등록(`POST`)/수정(`PUT`)은 로그인한 사람이면 누구나, 삭제(`DELETE`)는 `role=admin`인 사람만 되도록 각 엔드포인트에 `Depends(auth.require_user)` / `Depends(auth.require_admin)`을 붙임.
4. `app_frontend.py` — 앱 진입 시 로그인 화면을 먼저 보여주고, 로그인 성공하면 이메일/비밀번호로 받은 토큰을 이후 모든 등록/수정/삭제 요청에 실어 보냄. "회원 삭제" 메뉴 자체도 관리자가 아니면 사이드바에 안 보이게 숨김(화면에서도 안 보이고, 혹시 API를 직접 두드려도 서버가 한 번 더 막음 — "이중 방어").

**왜**: 피드백 #2 — "실배포 시 로그인 관리로 아무나 로그인 못하게, 삭제는 등록자/담당자만." 두 단계 역할(직원=등록·수정 가능/삭제 불가, 관리자=전부 가능)로 결정함(사용자 확인 완료).

**검증**: 잘못된 이메일/비밀번호로 로그인 시도 → 정상적으로 거부됨. 토큰 없이 회원 등록/삭제 API를 직접 호출 → 401(로그인 필요)로 차단됨. 실제 로그인 성공 흐름은 Supabase에 계정이 있어야 테스트 가능해서, 사용자가 SQL 실행 + 계정 생성 후 확인 예정.

**참고 개념**:
- **JWT(JSON Web Token)**: 로그인에 성공하면 서버가 "이 사람이 로그인했다"는 걸 증명하는 암호화된 문자열(토큰)을 하나 줍니다. 이후 요청마다 이 토큰을 같이 보내면, 서버는 매번 비밀번호를 다시 묻지 않고 토큰만 보고 "누구인지, 무슨 역할인지" 확인할 수 있습니다. 자동차 발렛 티켓과 비슷합니다 — 티켓(토큰)만 보여주면 다시 신분증(비밀번호) 안 보여줘도 되는 것.
- **JWKS(공개키 목록)**: 우리 서버가 "이 토큰이 진짜 Supabase가 만든 게 맞나"를 확인할 때 쓰는 열쇠 꾸러미입니다. Supabase가 공개적으로 제공하는 검증용 열쇠라서, 우리 서버는 비밀번호 없이도 토큰의 진위만 확인할 수 있습니다.
- **이중 방어(defense in depth)**: 화면(프론트엔드)에서 "삭제" 버튼을 숨기는 것만으로는 진짜 보안이 안 됩니다(개발자도구로 우회 가능). 그래서 서버(백엔드) 쪽에서도 한 번 더 권한을 확인하도록 만들었습니다 — 화면은 사용자 편의용, 서버 검사는 실제 보안용.
- **st.session_state**: Streamlit에서 로그인 정보처럼 "이 화면 저 화면 옮겨다녀도 기억해야 하는 값"을 담아두는 임시 저장소입니다. 브라우저 탭을 새로고침하면 초기화되니, 지금 방식은 완전한 "로그인 유지"는 아니고 세션(탭 하나) 단위 로그인입니다 — 나중에 필요하면 쿠키 기반으로 개선할 수 있습니다.

**⚠️ 다음 작업(노트북 포함) 전 필수**:
1. Supabase SQL Editor에서 `sql/003_add_profiles_and_auth.sql` 실행
2. Supabase 대시보드 → Authentication → Users → "Add user"로 계정 생성 (이메일/비밀번호 직접 입력)
3. 관리자로 만들 계정은 SQL Editor에서: `update profiles set role = 'admin' where email = '해당 이메일';`

## 2026-08-13 — #2 관련 버그 수정: 공유 Supabase 클라이언트가 요청 중간에 고장나던 문제

**무엇을**: `supabase_db.py`의 `_supabase()`에서 `@lru_cache`를 제거함. 이제 Supabase 클라이언트를 요청마다 새로 만듭니다(약간의 성능 손해는 있지만, 직원 몇 명이 쓰는 앱 규모에서는 무시할 수준).

**왜**: 로그인 기능을 붙이고 나서 실제로 등록을 시도했더니 "회원 등록 중 오류" 400 에러가 났고, 회원 목록도 갑자기 빈 배열만 나오는 증상을 사용자가 보고함. 재현/추적 결과:
- 원래 `_supabase()`는 `@lru_cache`로 서버가 켜져 있는 동안 클라이언트 인스턴스 하나를 계속 재사용하고 있었음(로그인 기능 추가 전부터 있던 코드).
- FastAPI는 `def`(동기 함수)로 만든 엔드포인트를 요청마다 별도 스레드에서 실행합니다. 로그인 기능을 추가하면서 거의 모든 요청(등록/수정/삭제뿐 아니라 권한 확인까지)이 이 하나의 공유 클라이언트를 동시에 여러 스레드에서 두드리게 됐고, 어느 시점부터 그 클라이언트의 내부 연결 상태가 꼬여서 조회는 빈 배열을, 등록/권한조회는 알 수 없는 오류를 돌려주기 시작함.
- 서버 프로세스를 완전히 재시작하면 일시적으로 정상화됐다가, 요청이 좀 쌓이면 다시 같은 증상이 나타나는 패턴으로 확인 — "재시작하면 낫는다"는 전형적인 상태 손상(state corruption) 버그의 특징.
- `@lru_cache` 제거 후 반복 테스트(연속 등록 3건, 목록 조회 8회, 관리자 삭제 6건)로 재발하지 않는 것 확인.

**참고 개념**:
- **연결 재사용(커넥션 풀) vs 매번 새로 연결**: 보통은 네트워크 연결을 재사용하는 게 더 빠르지만, 그 재사용 로직이 "여러 요청이 동시에 같은 연결을 건드려도 안전하다(thread-safe)"는 보장이 없으면 오히려 위험합니다. 이번 경우가 그런 경우였어요 — 안전성이 확인 안 된 재사용보다는, 조금 느려도 매번 새로 만드는 쪽이 더 신뢰할 수 있었습니다.
- 이런 "가끔 재시작해야 낫는" 버그는 보통 어딘가에 "여러 스레드/요청이 공유하는 상태"가 있고, 그게 서로 충돌할 때 생깁니다. 재시작하면 그 꼬인 상태가 초기화돼서 일시적으로 괜찮아 보이는 게 오히려 단서가 됩니다.

- **표시용 값 vs 저장되는 값**: "연번"처럼 화면에 보여줄 때만 계산하고 저장은 안 하는 값과, `member_no`처럼 한 번 정해지면 계속 유지되어야 하는 값을 구분하는 게 이번 설계의 핵심입니다. 저장이 필요 없는 걸 굳이 저장하면 나중에 값이 꼬일 여지만 늘어납니다.

- **쿠키(cookie)**: 브라우저에 아주 작은 정보를 저장해뒀다가, 같은 사이트에 다시 접속할 때 서버가 다시 읽을 수 있게 하는 표준 기술입니다. 여기서는 "이 사람이 로그인했었다"는 증표(refresh_token)를 쿠키에 담아뒀다가, 페이지를 새로 열 때 그 증표로 자동 로그인을 시도합니다.
- **refresh_token vs access_token**: `access_token`은 유효기간이 짧고(1시간) API 요청마다 실제로 쓰이는 "출입증"입니다. `refresh_token`은 유효기간이 훨씬 길고, "출입증을 새로 발급받을 수 있는 자격"만 증명합니다. 출입증(access_token)을 오래 유지되는 곳(쿠키)에 두면 탈취됐을 때 위험이 크므로, 오래 두는 건 refresh_token만이고 access_token은 매번 새로 받습니다.

**후속 버그 수정 (2026-08-14)**: 로그인 유지가 실제로는 동작 안 하는 문제가 2건 있었음, 둘 다 수정 후 사용자가 브라우저에서 정상 동작 확인:
1. `st.cache_resource`로 `CookieManager`를 감쌌더니 "CachedWidgetWarning" 에러 발생 — CookieManager는 내부적으로 위젯처럼 동작해서 캐시 데코레이터 안에 두면 안 됨. 캐싱 제거하고 매 실행마다 새로 만들되 `key`를 고정해서 해결.
2. 쿠키를 브라우저에 저장(`cookie_manager.set()`)한 직후 바로 `st.rerun()`을 불러서, 브라우저가 실제로 쿠키를 저장할 시간도 없이 화면이 바뀌어버리는 경쟁 상태(race condition)가 있었음. 로그인 성공 시 `st.rerun()`을 강제로 부르지 않고 스크립트가 자연스럽게 끝까지 이어지도록(같은 실행 안에서 로그인 화면 대신 바로 메인 화면까지 그려지도록) 구조를 바꿔서 해결. 이제 새로고침하면 로그인 화면이 아주 잠깐 비쳤다가 자동으로 메인 화면으로 넘어가는 정도로 동작함(정상).

## 2026-08-14 — #6 AI 추천 조회를 백그라운드로 전환 (메뉴 이동해도 안 끊기게)

**무엇을**:
1. `main.py`의 `fetch_initial_recommendations` 엔드포인트 로직을 순수 함수 `_compute_initial_recommendations(client_id)`로 분리(FastAPI 라우팅과 분리해서, 스레드에서도 그냥 호출할 수 있게).
2. 메모리 안에 작업 상태를 담아두는 간단한 저장소(`_recommend_jobs` 딕셔너리)를 만들고, `POST /api/recommend/start`로 백그라운드 스레드에서 조회를 시작 → 즉시 `{"status":"running"}` 응답 → `GET /api/recommend/status/{client_id}`로 진행 상태(`running`/`done`/`error`/`none`) 확인하는 구조로 바꿈. 기존의 한 번에 다 처리하던 `/api/recommend/fetch_initial`은 제거.
3. `app_frontend.py`의 "추천 복지 서비스" 화면을 이 상태값에 맞춰 다시 그림: `running`이면 2초마다 자동으로 상태를 다시 확인(`time.sleep(2); st.rerun()`), `done`이면 결과를 채워서 보여줌. "대화 초기화" 버튼은 이제 화면만 지우는 게 아니라 서버에 새 조회를 다시 요청함.

**왜**: 피드백 #6 — "한 메뉴에서 기능을 수행하다가 다른 메뉴로 넘어가면 먼저 실행하던 기능이 정지되는 것 같다." 원인은 Streamlit의 동작 방식 자체(사용자가 뭔가 하면 파이썬 스크립트를 처음부터 다시 실행) 때문에, AI 추천처럼 몇 초~몇십 초 걸리는 작업을 화면(Streamlit) 쪽에서 기다리고 있으면 메뉴를 옮기는 순간 그 기다림 자체가 사라져 버렸던 것. 조회 작업 자체를 화면이 아니라 서버(FastAPI 백엔드)에서 돌아가는 별도 스레드로 옮겨서, 화면이 뭘 하든 서버 쪽 작업은 안 끊기게 만듦.

**검증**: `curl`로 `/start` 호출 직후 응답이 0.1초 안에 옴(작업이 논블로킹으로 시작됨) 확인. 그 사이 다른 API(`/api/clients`) 요청도 즉시 응답되는 것 확인(작업이 서버 전체를 막지 않음). 몇 초 후 `/status`로 폴링하니 `done` 상태와 함께 정상적인 추천 결과(장애인가구 회원에게 장애인자립자금대여 등이 참고가 아니라 바로 추천되는 것 포함)가 돌아오는 것 확인.

**참고 개념**:
- **동기(synchronous) vs 백그라운드(background) 실행**: "동기"는 요청한 사람이 결과가 나올 때까지 그 자리에서 계속 기다리는 방식이고, "백그라운드"는 일단 "시작했다"고만 알려주고 실제 작업은 뒤에서 따로 진행되는 방식입니다. 오래 걸리는 작업일수록 백그라운드로 돌리고 "다 됐는지"는 나중에 따로 물어보는(폴링, polling) 구조가 화면이 멈추거나 끊기는 걸 막아줍니다.
- **스레드(thread)**: 한 프로그램 안에서 여러 작업을 "동시에" 진행하는 단위입니다. 여기서는 AI 추천 조회를 별도 스레드에 맡겨서, 그 스레드가 일하는 동안에도 서버는 다른 사람들의 다른 요청(회원 목록 조회 등)을 계속 처리할 수 있습니다.
- **폴링(polling)**: "혹시 다 됐어요?"를 주기적으로 계속 물어보는 방식입니다. 여기서는 화면이 2초마다 서버에 "그 작업 다 됐어?"라고 물어보다가, "다 됐다"는 답이 오면 그때 결과를 화면에 채워 넣습니다.

## 2026-08-14 — #8 사진 촬영 + 자동 문서화

**무엇을**:
1. **사진 촬영**: 신규 회원 등록/회원 수정 화면에 `st.camera_input()`(브라우저 카메라, 태블릿/휴대폰에서도 바로 동작) 추가. 촬영한 사진은 800x800 이하로 리사이즈 + JPEG로 압축해서 base64 텍스트로 인코딩 후 DB에 저장(`clients.photo_data`, `sql/006_add_photo.sql`). 별도 파일 저장소(Supabase Storage) 없이 기존 DB 접근 권한 그대로 보호됨.
2. **목록 조회 성능 보호**: `get_all_clients()`(회원 목록/통계 등에서 씀)는 `photo_data`를 아예 빼고 조회하도록 분리(`_LIST_COLUMNS`). 사진은 회원 한 명을 볼 때(`get_client`)만 같이 옴 - 목록에 회원이 늘어나도 사진 때문에 느려지지 않음.
3. **자동 문서화**: 새 모듈 `document.py` - Jinja2로 회원 정보(사진 포함)를 인쇄용 HTML로 만듦. PDF 라이브러리를 새로 설치하지 않고, 직원이 다운로드한 HTML을 브라우저에서 열어 인쇄(Ctrl+P) → "PDF로 저장"하면 그대로 서류/PDF가 되는 방식. 새 메뉴 "회원 서류 출력" 추가 (미리보기 + 다운로드).
4. **보안 정리**: 회원 목록/단건조회/주소검색/통계 API에 로그인 필요(`Depends(auth.require_user)`)를 빠짐없이 추가함 - 지금까지는 이 엔드포인트들이 로그인 없이도 호출 가능했던 빈틈이 있었음(사진처럼 민감한 정보가 추가되는 김에 같이 막음).

**왜**: 피드백 #8 — "회원 등록 시 사진 촬영 기능, 서류로 자동 문서화."

**검증**: `sql/006_add_photo.sql`을 아직 실행 전이라(자는 동안이라 실행 못 함) 실제 사진 저장은 끝까지 테스트 못 했지만, ① 테스트 이미지를 base64로 만들어 등록 시도 → 예상대로 "컬럼 없음" 오류로 실패하는 것 확인(마이그레이션 필요성 재확인), ② **사진 없는 기존 회원으로 서류 생성은 정상 동작 확인**(HTML 200 응답, "사진 없음" 표시 정상) - `photo_data` 컬럼이 아직 없어도 기존 기능(목록/조회/서류생성)이 전혀 안 깨지는 것까지 확인함(설계상 의도된 하위호환).

**⚠️ 다음에 꼭 해야 할 것**: Supabase SQL Editor에서 `sql/006_add_photo.sql` 실행 필요 - 이거 하기 전엔 사진 촬영 후 등록/수정 시 "회원 등록 중 오류" 남. 실행 후 브라우저에서 카메라 촬영 → 등록 → "회원 서류 출력" 메뉴에서 확인 부탁.

**참고 개념**:
- **base64 인코딩**: 사진 같은 이진 데이터(바이트)를 텍스트로 바꾸는 방법입니다. DB의 일반 텍스트 컬럼에 사진을 "글자처럼" 저장할 수 있게 해줍니다. 대신 원본보다 텍스트 길이가 좀 더 길어집니다(그래서 미리 리사이즈해서 크기를 줄여둠).

## 2026-08-14 — 회원 등록 신청서/개인정보 동의서를 실제 종이 양식 기준으로 재작성 + docx 전환 + 엑셀등록 통합

**무엇을**:
1. **문서 형식 전환**: `document.py`를 Jinja2/HTML에서 `python-docx` 기반으로 새로 작성. 결과물은 `.docx` 파일 하나(A4, 2페이지: 1p=회원 등록 신청서, 2p=개인정보 등 수집 및 이용 동의서). `main.py`의 서류 엔드포인트가 이제 docx 파일을 돌려주고, 프론트 "회원 서류 출력" 메뉴도 `.docx` 다운로드 버튼으로 변경(HTML 미리보기 iframe 제거).
2. **DB에 새 항목 9개 추가** (`sql/007_add_intake_fields.sql`): `emergency_contact_name/relation/phone`(비상연락망), `join_route`(가입경로), `has_illness`/`illness_type`(질병유무/종류), `has_career`/`career_type`(경력·전직업 유무/종류), `counselor`(상담자). 기존 종이 "이용신청서" 양식에는 있었지만 온라인 등록 화면엔 없던 항목들 - 사용자가 실제 서식 사진 3장을 보내줘서 확인 후 반영함.
3. **등록/수정 화면에 위 항목 입력 UI 추가**: 비상연락망 3칸, 가입경로(선택지+기타 사유), 질병유무(있다면 종류 다중선택+기타), 경력유무(있다면 직업군 다중선택+기타), 상담자(담당자명).
4. **"동거형태"는 별도 필드를 새로 안 만들고 기존 "가구유형"을 재사용**하기로 함 - 종이 양식의 동거형태(독거/노인부부/자녀가족/조손가정/기타)와 이미 만들어둔 가구유형(독거노인/노인부부/조손가정 등)이 개념이 겹쳐서, 같은 걸 두 번 입력받지 않게 하려고 문서의 "동거형태" 칸에 가구유형 값을 그대로 표시함.
5. **개인정보 동의서(2페이지)는 사용자가 보내준 실제 양식 문구를 그대로 옮김** - 목적/수집항목/보유기간/동의거부권리를 표로 정리하고, 마지막 줄에 실제 동의 여부(☑/☐)를 회원이 등록 시 체크한 값 그대로 반영. 기관명("구립응암노인복지관")은 `document.py` 맨 위 `ORG_NAME` 상수 하나만 바꾸면 전체 문서에 반영되도록 함.
6. **관심있는 서비스/관심있는 것은?/상담결과는 빈 칸으로, "특이사항"은 제외** - 사용자 요청대로.
7. **엑셀 일괄등록을 "신규 회원 등록" 화면 안으로 이동** (`st.expander`로) - 더 이상 별도 사이드바 메뉴가 아니라, 회원 한 명 등록 폼 아래 같은 페이지에 있음. 메뉴 이동 없이 등록 방식만 바꿔 쓸 수 있음.

**왜**: 사용자가 실제 복지관에서 쓰는 종이 서식(이용신청서/이용서약서/개인정보동의서) 사진을 보내주며, 온라인 등록에도 이 내용이 반영되어야 한다고 요청. 이용서약서는 지금 단계에서 불필요하다고 판단해 제외. 문서 형식은 "다운로드 없는 인쇄"가 아니라 "다운로드하는 docx"로 확정(사용자 확인).

**검증**: 실제 API로 회원 등록(비상연락망/가입경로/질병/경력/상담자 값 포함) → 문서 생성 → python-docx로 표 내용 다시 읽어서 입력한 값이 문서에 정확히 반영되는지 전부 확인. 동의 여부(☑/☐) 체크마크도 저장된 동의 값에 맞게 정확히 표시되는 것 확인.

**버그 수정**: docx 파일명에 한글이 들어간 `Content-Disposition` 헤더 때문에 500 오류 발생 → HTTP 헤더는 영문(ASCII/latin-1)만 담을 수 있어서, RFC 5987 방식(`filename*=UTF-8''...`)으로 인코딩하도록 수정.

**참고 개념**:
- **python-docx**: 파이썬으로 워드 문서(.docx)를 직접 만드는 라이브러리입니다. HTML+브라우저 인쇄 방식과 달리, 표/사진이 들어간 정식 문서 파일을 바로 만들어내고, 받는 사람이 워드나 한글에서 열어 편집도 할 수 있습니다.
- **HTTP 헤더 인코딩 제약**: 웹 요청/응답의 "헤더"(부가 정보를 담는 부분, 여기선 파일명)는 옛날 규격 때문에 영어/숫자만 안전하게 담을 수 있습니다. 한글 파일명을 보내려면 `RFC 5987`이라는 표준 방식으로 별도 인코딩해서 넣어야 합니다 - 이런 자잘한 규격 문제는 실제로 겪어보기 전엔 알기 어려운, 전형적인 "웹 표준 때문에 생기는 버그"입니다.
